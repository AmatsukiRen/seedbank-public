# 仓库迁移计划

## 两个仓库的分工

原研发库继续私有，保存历史实现、阶段报告与设计依据。本库作为未来公开的产品库，创建时同样为 PRIVATE，目前先维护页面、README、品牌和发行草稿。

应用迁移完成并经用户验收后，本库成为后续产品开发的主入口。原库保留为档案，避免长期手工维护两份代码。迁移期间的新修复须逐项记录，在切换前同步一次。

## 本次迁入范围

迁入对外页面、已认可头像与三张既有人工隔离场景的研发截图，维护中文、英文、日文的页面、README 和完整故事，重写仓库规划、版本规划、素材说明和用户验收步骤。没有迁入应用源码、旧 Git 历史、真实生命包、连接设置、运行日志、二进制程序或第三方模型。

## 后续源码候选

| 内容 | 迁移要求 |
| --- | --- |
| Python 核心、CLI、Qt Quick | 以当前工作区实现为准，连同需要的资源逐文件整理，不能直接用旧提交代替最新代码 |
| 开放出生与兼容种子 | 默认保留开放出生；旧种子按读取及打包依赖评估，不直接删除 |
| 离线测试与人工 fixture | 保留可公开的人工样本，统一执行入口，执行留给用户 |
| 正式打包与启动器 | 整理运行依赖、通用路径、固定入口图标与版本来源 |
| 协议与用户文档 | 重组为开始使用、记忆与来源、模型与费用、外观、备份与恢复、故障排查及开发说明 |
| 其他适配器、运行器与例子 | 按首发范围逐项决定，不整目录默认复制 |

应用迁移时保留项目 MIT 版权与贡献归属，不复制旧 `.git`。`.gitignore` 只是后续防护，不能替代实际导出清单的审阅。

## 公开前需要解决

- 将研发时的个人路径改为通用的首次使用与导入流程。
- 清理“一颗蛋变成一条鱼”等旧品牌描述，采用开放出生的当前定义。
- 保留原启动与图标故障记录，取得修正版的实际用户验收结果。
- 为品牌与第三方素材整理明确来源与使用范围。
- 对外展示只用人工包的真实截图，使用文档不附个人目录和内部原始日志。
- 首发版本统一为 0.0.1；档案格式版本保留各自的兼容规则。

后续顺序见[发行计划](release-plan.md)。当前新库的建立不意味着已经满足公开或发行条件。
